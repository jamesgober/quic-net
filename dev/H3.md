# The h3 engine - HTTP/3 and QPACK plan

> The plan for HTTP/3 (RFC 9114) and QPACK (RFC 9204) on top of quic-net. It lives here until the crate has a name; "the h3 engine" stands for it throughout. Nothing below is built yet.

---

## 1. Purpose

An HTTP/3 engine that does no I/O itself, the way http-net is for HTTP/1.1 and h2-net for HTTP/2. It runs on a quic-net `Connection`. HTTP/3 frames go on QUIC streams, field sections are compressed with QPACK, and requests and responses are handed over as the same http-net types the other two engines use. A service written for serve-net then answers HTTP/1.1, HTTP/2, and HTTP/3 alike.

## 2. Where it lives

Its own crate, like h2-net, depending on:

| Crate | For |
|---|---|
| quic-net | the connection and its streams |
| h2-net | the Huffman code (`hpack::huffman`) and the bounded field list (`hpack::HeaderList`); QPACK uses HPACK's Huffman table unchanged (RFC 9204 section 4.1.2) |
| http-net | the request and response types, and the strict HTTP/1.1 rules a field section must also pass, as h2-net does |

**Not inside quic-net.** QUIC is a transport that other protocols use too (DNS over QUIC, for one), and quic-net should not carry HTTP.

**Not inside h2-net.** HTTP/2 and HTTP/3 share semantics but not framing, flow control, or compression state.

## 4. Layers

1. **Frames** (RFC 9114 section 7): `DATA`, `HEADERS`, `CANCEL_PUSH`, `SETTINGS`, `PUSH_PROMISE` (refused), `GOAWAY`, `MAX_PUSH_ID`. Reserved and unknown types are skipped, counted, and bounded. The codec is sans-IO and fuzzed, and `decode(encode(f)) == f`.
2. **Stream types** (section 6.2): control (`0x00`), push (`0x01`, refused), the QPACK encoder (`0x02`) and decoder (`0x03`) streams, and reserved types skipped. Each critical stream is opened once; a second one, or a closed one, is `H3_CLOSED_CRITICAL_STREAM` or `H3_STREAM_CREATION_ERROR`.
3. **QPACK** (RFC 9204):
   - the 99-entry static table;
   - a dynamic table bounded by `SETTINGS_QPACK_MAX_TABLE_CAPACITY`;
   - encoder and decoder instructions, the Required Insert Count and Base, and acknowledgements;
   - blocked streams, bounded by `SETTINGS_QPACK_BLOCKED_STREAMS`.

   The encoder may use the static table only, and starts that way (section 6, idea I-1).
4. **The connection**: `SETTINGS` first on the control stream, then request streams. A request stream carries `HEADERS`, `DATA`, and optionally trailing `HEADERS`. `GOAWAY` drains gracefully, and errors are mapped to `H3_*` codes and stream resets.
5. **HTTP semantics**: pseudo-headers checked as section 4.3 says, connection-specific fields refused (section 4.2), then mapped to http-net's types through the same strict rules HTTP/1.1 follows. `Content-Length` must match the `DATA` received, or the result is `H3_MESSAGE_ERROR`.

## 5. What quic-net must provide

Already there: streams both ways with flow control, opening unidirectional streams, `STOP_SENDING` and `RESET_STREAM`, application close codes, and events for opened and readable streams.

Needed, for quic-net's roadmap:

- **A writable event.** `Event::StreamWritable(id)`, when a stream's send buffer or credit frees up after `stream_write` accepted less than offered. Without it, a writer can only poll.
- **Send order.** The control and QPACK streams must not wait behind bulk `DATA`. Either a per-stream urgency (also the base for RFC 9218) or "control first" ordering is needed; today the order is round robin.
- **Stream data in bulk.** A way to read a stream's contiguous data without copying it out first; QPACK and frame parsing want slices. Planned as an optimisation, measured first.
- Later: 0-RTT (quic-net 0.8), for requests in the first flight; DATAGRAM frames (RFC 9221), for RFC 9297.

## 6. Threats

| Threat | Defence | Cost |
|---|---|---|
| QPACK dynamic table memory | capacity bounded by our `SETTINGS_QPACK_MAX_TABLE_CAPACITY` (default 4 KiB, 0 allowed) | the table's bytes, per connection |
| a "QPACK bomb": a small field section referencing large entries many times | a decoded-size budget (`SETTINGS_MAX_FIELD_SECTION_SIZE`) checked as each field is added, before it is copied, as h2-net does for HPACK | one comparison per field |
| blocked streams holding memory | at most `SETTINGS_QPACK_BLOCKED_STREAMS` (default 16) blocked; more is `QPACK_DECOMPRESSION_FAILED` | the blocked field sections, bounded by the field section budget times the count |
| encoder stream floods | instructions consumed with a byte budget per unit of request data; table insertions beyond capacity refused | a counter |
| request smuggling through header mapping | connection-specific fields refused; pseudo-header rules enforced; values checked against the field-value grammar (QPACK carries any byte, CR and LF included); mapping through http-net's strict rules | the checks HTTP/1.1 already pays |
| `Content-Length` disagreeing with `DATA` | a mismatch is `H3_MESSAGE_ERROR` on the stream | a counter per stream |
| control stream abuse | a second `SETTINGS`, frames before `SETTINGS`, or a closed control stream is a connection error | none |
| unknown frame and stream type floods | skipped, but counted per connection; past a budget, `H3_EXCESSIVE_LOAD` | a counter |
| stream exhaustion | QUIC's stream limits; requests past `GOAWAY` refused | none |

Every budget is a setting with a secure default; a deployment may change it (the stack's rule: nothing security-relevant hard-coded).

## 7. Ideas and experiments

- **I-1: a static-only QPACK encoder by default.**
  - *Hypothesis:* for typical API traffic, the dynamic table saves little next to the static table and Huffman, and costs memory per connection, head-of-line blocking (blocked streams), and an encoder-stream attack surface.
  - *Method:* encode recorded header sets (browser page loads, API calls) both ways. Measure bytes on the wire, CPU per field section, and memory per connection.
  - *Expected cost:* a few percent more header bytes on long-lived browser connections; none for short API calls.
  - *The decoder* supports the dynamic table either way, since peers may use it.
- **I-2: one mapping for three protocols.** Run HTTP/3 field sections through the same http-net validation HTTP/1.1 and HTTP/2 use (h2-net already does this). The three engines then cannot disagree about what a request means.
  - *Method:* the differential idea proxy-net uses (idea I-6 there). The same request is sent as HTTP/1.1, HTTP/2, and HTTP/3, and the decoded results must be equal.
  - *Cost:* the validation HTTP/1.1 already pays.

## 10. QPACK design

QPACK is designed as a sans-IO module with no dependency on quic-net, so it moves into the h3 engine's crate unchanged once that exists. It sees bytes and stream numbers, never streams.

### 10.1 What it reuses from h2-net

| Item | Use | Status in h2-net 0.3.1 |
|---|---|---|
| `hpack::huffman::{encode, decode, encoded_len}` | string literals (RFC 9204 section 4.1.2 uses HPACK's Huffman code) | public |
| `hpack::HeaderList`, `HeaderField` (with `sensitive`) | decoded field sections, with the decoded-size budget checked as each field is added | public, but `HeaderList::push` is crate-private |
| prefixed integers (`hpack::int`) | every QPACK integer (RFC 7541 section 5.1, shared) | crate-private |

**Asked of h2-net:** make `HeaderList::push` public (it already enforces the budget), and export the prefixed-integer encoder and decoder. If h2-net would rather not, the engine carries its own integer code (about 60 lines, fuzzed) and a field list of its own; the request is for one implementation instead of two.

### 10.2 Types

- **The static table**: RFC 9204 appendix A's 99 entries as a constant array, with two lookups built at compile time as sorted arrays and searched by binary search: (name, value) to index, and name to the first index.
- **The dynamic table**: entries in insertion order, each name and value in one allocation.
  - An entry's size is name plus value plus 32 (section 3.2.1).
  - The table tracks its capacity, the absolute index of the next insertion, and how many entries were evicted.
  - Eviction takes the oldest entries. On the encoder side it never evicts an entry that a field section the decoder has not yet acknowledged still references (section 2.1.1).
- **`Decoder`**:
  - `on_encoder_stream(bytes)` takes encoder instructions: Set Dynamic Table Capacity, Insert with Name Reference, Insert with Literal Name, Duplicate. A partial instruction is buffered, at most the table capacity plus 64 bytes.
  - `decode(stream, block, &mut HeaderList) -> Decoded` returns `Done`, or `Blocked` when the Required Insert Count is ahead of the table.
    - A blocked block is kept, counted against `SETTINGS_QPACK_BLOCKED_STREAMS`, and its bytes against the field section budget times that count.
    - `unblocked()` names the streams to retry after an insertion.
  - `cancel(stream)` covers a stream reset while blocked.
  - `instructions(&mut out)` writes the decoder stream's Section Acknowledgement, Stream Cancellation, and Insert Count Increment.
- **`Encoder`**:
  - `encode(stream, fields, &mut block, &mut encoder_stream)` encodes a field section.
  - `on_decoder_stream(bytes)` takes the peer's acknowledgements.
  - The encoder has two modes: static only (the default, idea I-1), or dynamic within the peer's capacity and blocked-stream limit.
  - It keeps, per stream, the Required Insert Count of each section not yet acknowledged, so eviction knows what is still referenced.

### 10.3 Wire details that go wrong

- **Required Insert Count** is sent modulo `2 * MaxEntries` (section 4.5.1.1). The decoder reconstructs it and refuses a value that cannot be reconstructed, and refuses 0 when the table was used.
- **Base**: a sign bit plus a delta. A Base below zero, or a post-base index past the Required Insert Count, is `QPACK_DECOMPRESSION_FAILED`.
- **Indexes**: relative, post-base, and absolute (encoder stream) each have their own arithmetic and their own off-by-one; each is tested at its edges.
- **The never-indexed bit (N)** survives decoding as `HeaderField::sensitive`, and the encoder never inserts a sensitive field into the dynamic table (section 7.1).
- **Insert Count Increment** of 0, or past what the encoder inserted, is `QPACK_DECODER_STREAM_ERROR`.
- **A Section Acknowledgement** for a stream with nothing outstanding is `QPACK_DECODER_STREAM_ERROR`.
- **A reference to an evicted entry** is `QPACK_DECOMPRESSION_FAILED`, and so is a Duplicate of one.

### 10.4 Budgets

| What | Default | Why |
|---|---|---|
| dynamic table capacity we accept (`SETTINGS_QPACK_MAX_TABLE_CAPACITY`) | 4,096 bytes | the HPACK default; memory per connection stays small |
| blocked streams (`SETTINGS_QPACK_BLOCKED_STREAMS`) | 16 | bounds memory held for blocked sections |
| decoded field section (`SETTINGS_MAX_FIELD_SECTION_SIZE`) | 16 KiB | checked as each field is added, before it is copied, so a small block referencing large entries cannot grow past it |
| a partial encoder instruction | table capacity + 64 bytes | an insertion cannot be larger than the table |
| encoder-stream bytes buffered | 64 KiB | refuses a peer that streams instructions faster than it uses them |

All are settings with these defaults.

### 10.5 Tests and fuzzing

- RFC 9204 appendix B's examples, byte for byte, both ways.
- The QPACK interop corpus (offline field sections encoded by other implementations, with their decoded forms), as test data only. Its licence is to be checked before it is copied in.
- Round trips: random field sections, through both encoder modes, random table capacities, and acknowledgements delayed and reordered. Every section must decode to what was encoded.
- Fuzz targets:
  - field section decoding against an arbitrary table state;
  - encoder-stream instructions;
  - decoder-stream instructions;
  - the round trip above.

### 10.6 Costs, estimated until measured

- Static-only encoding: one binary search per field plus Huffman, about the cost of HPACK's encoder without its table.
- Decoding: one pass over the block. Each field is copied once into the list, after its size is checked against the budget.
- Memory per connection: the dynamic table (4 KiB by default) plus blocked sections, both bounded above.

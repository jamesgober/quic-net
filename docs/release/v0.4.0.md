# quic-net v0.4.0 - Streams and flow control

**Streams in any order, over any loss, within their limits.** Reassembly, the final size rules, reset and stop on the receiving side; buffering, retransmission, and acknowledgement on the sending side; flow control for streams and the connection, both ways; stream limits; CRYPTO reassembly.

```rust
use quic_net::{RecvCredit, RecvStream};

let mut conn = RecvCredit::new(1 << 20);
let mut stream = RecvStream::new(256 * 1024);
// A STREAM frame:
let growth = stream.on_stream(offset, data, fin)?;
conn.receive_more(growth)?;
// The application reads:
let n = stream.read(&mut buf);
conn.consumed(stream.take_consumed());
if let Some(max) = stream.update() { /* send MAX_STREAM_DATA */ }
```

## What is quic-net?

QUIC (RFC 9000) for Rust, built up from its parts on net-io's UDP socket and tls-net's TLS 1.3. 0.2 was the wire format, 0.3 its protection; this release carries data.

## What's in 0.4.0

- **Receiving.** `RecvStream` takes data in any order, keeps the first copy of a byte, and stores it at its offset, so a hostile order costs no more than an in-order one. Every frame is checked against the final size and the stream's limit before a byte is stored. A reset drops unread data and counts it, so the connection's credit moves on.
- **Sending.** `SendStream` keeps written bytes until they are acknowledged, sends lost data first, and takes credit only for bytes never sent before. Acknowledgements may come in any order.
- **Flow control.** `RecvCredit` and `SendCredit`, for streams and the connection. Updates go out once half a window was read, not on every read.
- **Stream limits.** `LocalStreams` and `RemoteStreams`, and `StreamId` with the checks for frames on the wrong kind of stream.
- **CRYPTO.** `CryptoRecv` reassembles the handshake's data, up to 64 KiB past what TLS has read.

## Limits

| What | Bound |
|---|---|
| unread data per stream | its window |
| separate pieces of unread data per stream | 1,024 |
| CRYPTO data past what TLS read | 64 KiB per level |

## Tested

- A stream end to end over a channel that loses, duplicates, and reorders packets and loses acknowledgements, with stream and connection flow control: 300 runs, every byte delivered in order, both sides ending clean.
- A new `streams` fuzz target runs a receive stream under arbitrary frames, resets, stops, and reads, and the same channel model driven by the input.

## Costs

On Linux under load, so upper bounds:

| Path | Cost |
|---|---|
| send 1,200 bytes (write, chunk, frame, acknowledge) | 34 ns |
| receive 1,200 bytes in order and read them | 21 ns |
| receive two 1,200-byte chunks out of order and read them | 64 ns |

## Known gaps

- No connection yet: these parts wait for the handshake, which waits for tls-net's QUIC interface (`dev/PLAN.md` section 5).
- net-io's UDP lacks GSO, GRO, ECN, and the don't-fragment bit (also section 5).

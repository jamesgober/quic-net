# quic-net v0.7.0 - Migration

**The connection follows a client to a new address, once the address is proved.** NAT rebinding, a phone moving networks, and a client that migrates on purpose to a fresh connection ID all keep the connection, and a spoofed or replayed packet moves nothing.

```rust
// The loop now says where datagrams come from, and where they go:
conn.handle_datagram(now, from, &mut datagram);
while let Some(to) = conn.poll_transmit(now, &mut out) {
    socket.send_to(&out, to)?;
}
// A client that changed its socket:
conn.migrate(now)?;
```

## What is quic-net?

QUIC (RFC 9000) for Rust, sans-IO: the caller owns the socket and the clock.

## What's in 0.7.0

- **Paths and path validation** (RFC 9000 sections 8 and 9). The server follows a client whose newest non-probing packet comes from a new address. Until the address answers a `PATH_CHALLENGE`, it sends there within three times what it receives. It returns to the previous path if the challenge goes unanswered.
- **Congestion state per network**: a new IP address resets it; a port change alone (NAT rebinding) keeps it.
- **Connection IDs** issued to the peer and replaced when it retires one, with events so the caller can route them.
- **`migrate()`** for a client whose socket changed: it moves to a fresh connection ID of the server's, so an observer cannot link the two paths, and proves the new path.

## Changed

- `handle_datagram(now, from, data)`, `poll_transmit(now, out) -> Option<SocketAddr>`, and the peer's address in `Connection::client` and `Connection::server`.

## Fixed

- A path challenge's resend timer outlived the challenge, so `poll_timeout` kept reporting a time already past.

## Tested

NAT rebinding during a transfer; a client migrating to a new network mid-transfer; a packet replayed from another address; a brief rebinding that returns; the server issuing IDs. The `connection` fuzz target now also delivers datagrams from another address.

# quic-net v0.3.0 - Packet protection

**Header protection and packet protection, done around key traits.** The Initial key schedule, sealing and opening in place, the AEAD limits, and the Retry integrity tag, checked byte for byte against RFC 9001's test vectors.

```rust
use quic_net::{InitialSecrets, open_payload, parse_packet, remove_header_protection};

let secrets = InitialSecrets::new(&dcid)?;
let keys = secrets.client.key_material(16)?; // AEAD key, IV, header key
// ... make a PacketKey and a HeaderKey from them, then for a received packet:
let pn_offset = parse_packet(&datagram, 8)?.pn_offset;
let unprotected = remove_header_protection(&mut datagram, pn_offset, largest_pn, &hp)?;
let frames_at = open_payload(&mut datagram, &unprotected, &key)?;
```

## What is quic-net?

QUIC (RFC 9000) for Rust, built up from its parts on net-io's UDP socket and tls-net's TLS 1.3. 0.2 was the wire format; this release protects it.

## What's in 0.3.0

- **Two key traits.** `PacketKey` seals and opens a payload in place, with the nonce made from the packet number and the header as associated data. `HeaderKey` turns a 16-byte sample into the header mask. A TLS session implements them; their shape matches rustls's QUIC keys.
- **Sealing and opening.** `seal_packet` encrypts the payload, writes the tag, and applies header protection. Opening is two steps: `remove_header_protection` recovers the packet number and the key phase, and `open_payload` authenticates and decrypts with the key the phase picks. The reserved bits are checked only after the payload authenticates, so a forged packet is dropped, never a connection error.
- **Keys.** `InitialSecrets` derives both Initial secrets from the client's first destination ID; `Secret::key_material` gives the key, IV, and header key, and `Secret::next` the secret after a key update. Secrets and key material are zeroed on drop.
- **AEAD limits.** `AeadUsage` counts packets sealed under the current key and forged packets under any key, against RFC 9001 section 6.6's limits for AES-GCM, ChaCha20-Poly1305, and AES-CCM.
- **Retry.** `retry_tag` and `verify_retry`, compared in constant time.
- **Tested against RFC 9001 appendix A**: the Initial keys, the client's 1,200-byte Initial, the server's Initial, the Retry, and the ChaCha20-Poly1305 short header packet, each sealed to the RFC's bytes and opened again. A new `protection` fuzz target checks round trips and arbitrary input.

## Costs

With the test ciphers (RustCrypto AES-128-GCM), on Linux under load, so upper bounds:

| Path | Cost |
|---|---|
| seal a 1,200-byte payload | 713 ns |
| open it | 740 ns |
| derive the Initial keys of both directions | 1.2 us |

The cipher is nearly all of it.

## Known gaps

- No cipher of its own: the keys come from tls-net once it has a QUIC interface. The connection API, the handshake, and streams wait on that (`dev/PLAN.md` section 5).
- net-io's UDP lacks GSO, GRO, ECN, and the don't-fragment bit (also section 5).

`0.4.0`: the connection, stream, and configuration APIs, keys from tls-net's QUIC interface, the handshake, streams, flow control, and address validation.
